# Implementation Roadmap and Engineering Notes

**Document 04 — From Concept to Deployable Shield**  
*Practical construction sequence for the Wald Module*

---

## Phase 0 — Minimal Viable Shield (Days to Weeks)

**Goal**: Demonstrate the value of the critic loop with almost no new infrastructure.

- Write a high-quality system prompt that embodies the Wald checklist (Document 03, Section 3).
- Implement a two-call pattern: primary model drafts → shield critiques → primary model revises.
- Manually seed a small Non-Survivor Store (a few dozen high-quality failure summaries and base-rate notes) and give the shield retrieval access to it.
- Measure: on a set of queries known to be survivor-biased (startup advice, “what works in X”, medical rare events, etc.), compare answers with and without the shield for presence of caveats, base-rate awareness, and reduced overconfidence.

This phase requires only prompt engineering and a simple retrieval index. It is sufficient to validate the concept.

## Phase 1 — Persistent Failure Memory (Weeks to Months)

- Design the schema for the Non-Survivor Store (region / domain, selection process description, observed survivor pattern, estimated or known non-survivor evidence, confidence, provenance).
- Build ingestion pipelines: 
  - Curated human entry.
  - Automated extraction from known post-mortem collections, replication trackers, and failure databases.
  - Optional user feedback (“this answer ignored a known failure mode”).
- Add access controls and versioning.
- Expand the shield’s retrieval to prefer this store when survivorship risk is detected.

## Phase 2 — Specialized Critic Model (Months)

- Collect a dataset of (query, draft answer, gold critique) triples, initially generated by strong models following the checklist and then human-refined.
- Fine-tune a smaller, faster model (or a LoRA on an existing model) to perform the Wald critique.
- Replace or augment the prompted LLM call with this specialized critic for latency and consistency.
- Continue to keep the checklist explicit so the behavior remains inspectable.

## Phase 3 — Deeper Integration

- Training-time use: critiques become preference pairs or contrastive examples for continued pre-training or RL.
- World-model and planning extensions: when the primary system imagines futures, the shield injects non-survivor trajectories (analogous to mixing accident data into driving world models).
- Evaluation suite: a public or internal benchmark that specifically scores models on their handling of survivor-biased questions, with the shield used as an automated judge component.
- Organizational deployment: the shield runs on internal knowledge bases so that company-specific silent failures are taken into account.

## Engineering Principles to Preserve

1. **Separation of concerns**. The primary model optimizes for useful generation on the data it has. The shield optimizes for correct treatment of the data it does not have. Do not collapse them into a single prompt if reliability matters.
2. **Structured output**. Critiques must be machine-readable so they can drive revision, logging, and measurement.
3. **Provenance**. Every non-survivor entry and every critique should record where the evidence (or the prior) came from.
4. **Humility about reconstruction**. The shield estimates vulnerability; it does not hallucinate specific lost aircraft. When evidence is absent it says so.
5. **Continuous updating**. The Non-Survivor Store is a living system. New failure modes are added as they are discovered.

## Success Criteria

- On survivor-biased queries, final answers contain explicit acknowledgment of missing failure data more often than baseline.
- Confidence is better calibrated: high-confidence claims are less likely to rest solely on survivor patterns.
- Users and downstream systems can inspect the shield’s reasoning.
- The overhead (latency, cost) remains acceptable for the use cases where the shield is enabled.

## Closing Note

Wald’s contribution was not a new alloy or a thicker plate. It was a method for deciding where the plate should go when the most important data are missing. The shield is that method, made operational for systems that learn from text. The armor goes where the holes are not.
